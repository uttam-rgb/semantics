# analytics.alerted_leads_log

**Status:** Part of the [lead-alerting/reporting system](_reporting_system_overview.md).

**Purpose (from the table's own Postgres comment):** *"Every lead that appeared in each alert sheet, logged at send time. Join to cratio_leads_analytics 24-48h later to measure resolution rate per alert type per owner."*

**Grain:** One row per (alert_date, alert_type, mobile_number, lead_owner) — enforced by a composite primary key, so this table is naturally idempotent per alert-send.

## Columns

| Column | Type | Nullable | Notes |
|---|---|---|---|
| alert_date | date | no | part of PK |
| alert_type | text | no | part of PK — 10 observed values, see [overview](_reporting_system_overview.md) for the mapping to `alert_metric_snapshots` columns: `instructor_priority_leads` (48,257), `overdue_followups_last_3_days` (45,917), `followups_due_today` (45,805), `stuck_50pct_payment` (40,561), `send_course_details` (21,560), `untapped_yesterday` (9,967), `no_followup_set` (4,873), `send_payment_links` (2,272), `not_contacted_7_days` (2,233), `hot_lead_priority` (1,646) |
| lead_owner | text | no | part of PK |
| mobile_number | text | no | part of PK — join key to `cratio_leads_analytics.mobile_number` |
| lead_stage_at_alert | text | yes | the lead's `lead_stage` at the moment it was alerted — a snapshot value, compare against current `cratio_leads_analytics.lead_stage` to see if it's moved |
| created_at | timestamp with tz | no, default now() | |

## Relationships

Conceptual joins (no enforced FK): `mobile_number` → `cratio_leads_analytics`; `(alert_date, alert_type, lead_owner)` → `alert_resolution_log`.

## Gotchas

- **`alert_type = 'overdue_followups_last_3_days'` is generated by logic that doesn't actually filter for overdue-ness** (includes future-dated followups, uses a 7-day not 3-day window) — see [`metrics/lead_health_alerts.md`](../../metrics/lead_health_alerts.md) for the confirmed bug and corrected formula.
